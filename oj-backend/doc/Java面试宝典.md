## 第二部分：技术深度面试

### 1. MySQL数据库

**面试官**：我们来聊聊数据库。在`亚克在线编程判题系统`中，用户提交记录这张表的数据量可能会很大。如果让你查询某个用户最近的10条提交记录，你会如何设计索引来优化查询速度？

**求职者**：这是一个很典型的SQL优化问题。用户提交记录表（`question_submit`）的核心字段应该有`id`、`userId`（用户ID）、`questionId`（题目ID）、`createTime`（提交时间）等。

要优化“查询某个用户最近的10条提交记录”这个操作，我会创建一个**联合索引**。具体来说，我会选择`userId`和`createTime`这两个字段建立联合索引，即 `KEY idx_userId_createTime (userId, createTime DESC)`。

这样设计的原因是：
1. **`userId`在前**：查询条件首先是`WHERE userId = ?`，将`userId`放在联合索引的最左边，可以充分利用**最左前缀原则**，快速定位到该用户的所有提交记录。
2. **`createTime`在后**：在找到该用户的所有记录后，我们需要按时间倒序排列（`ORDER BY createTime DESC`）并取出前10条。将`createTime`作为索引的第二部分，并且设置为`DESC`，这样索引本身就是按时间排好序的。数据库可以直接从索引中按顺序读取数据，避免了**文件排序（filesort）**，极大地提高了查询效率。

**面试官**：很好。那再问一个场景，当一个用户提交代码后，我们需要在`题目表`中将`提交数`这个字段加1，同时在`提交记录表`中插入一条新纪录。这个过程会涉及到并发问题吗？你们是如何保证数据一致性的？

**求职者**：这个场景确实会涉及到并发问题。想象一下，如果两个用户同时对同一道题目提交了代码，那么`题目表`的`提交数`字段可能会被并发更新，如果不加控制，可能导致更新丢失。

为了保证数据一致性，我们使用了数据库的**事务**和**锁机制**。
1. **事务**：我们将“更新题目提交数”和“插入提交记录”这两个操作放在同一个Spring的`@Transactional`事务方法中。这能保证这两个操作**要么都成功，要么都失败**，维护了业务上的原子性。
2. **锁机制**：在更新`提交数`时，MySQL的InnoDB引擎默认会对`UPDATE`操作的行加上**排他锁（行锁）**。当一个事务正在更新这行数据时，其他试图更新同一行的事务必须等待，直到前一个事务提交或回滚。这就避免了并发更新导致的数据不一致问题。

通过Spring的声明式事务和MySQL的行锁机制，我们就能在并发场景下，安全、可靠地完成这个业务操作。

**面试官**：你刚才提到的联合索引听起来很合理。那你能把完整的SQL查询语句写出来吗？

**求职者**：好的，完整的SQL语句如下：
```sql
SELECT id, questionId, status, createTime FROM question_submit WHERE userId = ? ORDER BY createTime DESC LIMIT 10;
```
配合我们之前创建的`KEY idx_userId_createTime (userId, createTime DESC)`索引，这条SQL语句的执行效率会非常高。Explain分析的结果会显示它使用了索引（`type: ref`），并且没有额外的排序操作（`Extra: Using index`）。

### 2. Redis缓存

**面试官**：我看到你的技术栈里有Redis。在`亚克在线编程判题系统`中，你会用Redis来做什么？

**求职者**：我会用Redis来做**缓存**，以提升系统性能和响应速度。具体来说，有几个可以缓存的热点数据：
1. **用户信息缓存**：用户登录后，其个人信息（如用户名、头像）在短时间内不会频繁变动，但会被频繁读取（例如显示在页面右上角）。我会将用户信息以`String`类型（JSON格式）存入Redis，并设置一个较短的过期时间（如30分钟）。
2. **题目信息缓存**：对于一些热门题目，其内容（题干、示例、判题配置）是固定的，但会被大量用户频繁查看。我会将这些题目信息缓存起来，当用户请求题目详情页时，优先从Redis读取，减轻数据库压力。
3. **排行榜缓存**：比如“用户通过题目数排行榜”，这种实时性要求不高但计算相对复杂的排行数据，非常适合用Redis的`Sorted Set`数据结构来实现。用户的ID作为`member`，通过的题目数作为`score`，可以非常方便地进行排序和查询。

**面试官**：那你如何保证Redis缓存和MySQL数据库的数据一致性呢？

**求职者**：这是一个经典的缓存与数据库一致性问题。在我的项目中，我会采用**Cache-Aside Pattern（旁路缓存模式）**，这也是最常用的一种策略。

具体操作如下：
1. **读操作**：
   - 应用先从Redis查询数据。
   - 如果缓存命中，则直接返回数据。
   - 如果缓存未命中，则从MySQL数据库查询数据。
   - 查到数据后，将数据写入Redis缓存，并设置一个过期时间，然后返回给应用。

2. **写操作（数据更新）**：
   - **先更新数据库，再删除缓存**。
   - 这么做的原因是，删除缓存操作非常快，而更新缓存操作相对较慢。如果先删除缓存再更新数据库，在并发场景下，可能会有另一个线程在数据库更新完成前读取了旧数据并写入缓存，导致数据不一致。
   - 而“先更新数据库，再删除缓存”的策略，即使删除缓存失败了，也只是导致后续的读请求会读到一次旧数据（缓存未命中，从数据库读旧数据再写回缓存），但在缓存过期后，数据会恢复一致。为了进一步保证，可以引入**消息队列**或**延时双删**的策略来确保缓存一定被删除。

通过这种方式，我们可以在绝大多数情况下保证数据的一致性，同时享受到缓存带来的性能提升。

**面试官**：你提到了用`Sorted Set`来实现排行榜，能具体解释一下`Sorted Set`是什么吗？以及在代码层面你会如何实现这个功能？

**求职者**：当然可以。`Sorted Set`（有序集合）是Redis的一种数据结构，它和普通的`Set`（集合）很像，都能存储不重复的元素。但它有一个关键区别：`Sorted Set`中的每个元素都会关联一个`double`类型的分数（score），Redis会根据这个分数对集合中的元素进行从小到大的排序。

在我的排行榜场景中：
- **`key`** 可以是 `user_ranking_list`。
- **`member`** 是用户的ID（`userId`）。
- **`score`** 是该用户通过的题目总数。

具体的代码实现（以Jedis或Lettuce客户端为例）会是这样：
1. **更新分数**：当用户每通过一道新题时，我们会使用`ZADD`命令来更新他的分数。`ZADD user_ranking_list <new_score> <userId>`。`ZADD`命令很方便，如果用户已存在，它会更新分数；如果不存在，则会新增。
2. **查询排行榜**：要获取排名前10的用户，我们会使用`ZREVRANGE`命令。`ZREVRANGE user_ranking_list 0 9 WITHSCORES`。这个命令会从分数最高（`REV`代表反向）的开始，取出索引从0到9的10个元素，`WITHSCORES`选项可以同时返回用户ID和他们的分数。

`Sorted Set`的底层数据结构是**跳跃表（Skip List）**和**哈希表（Hash Table）**的结合。哈希表用于存储`member`到`score`的映射，可以实现O(1)复杂度的`member`查找。跳跃表则用于存储所有元素并按`score`排序，可以实现O(logN)复杂度的范围查找和排序操作。这种设计使得`Sorted Set`在实现排行榜这类功能时非常高效。

**面试官**：在使用缓存时，除了数据一致性，你还考虑过其他潜在的问题吗？比如缓存穿透、缓存击穿和缓存雪崩？

**求职者**：考虑过。这三个是经典的缓存高可用问题，我们的设计中也需要有相应的对策：
1. **缓存穿透**：指查询一个数据库和缓存中都不存在的数据。这会导致每次请求都直接打到数据库，失去了缓存的意义。我的解决方案是**缓存空对象**。当数据库查询不到数据时，我依然在Redis中缓存一个特殊的空值（比如`"null"`），并设置一个较短的过期时间。这样后续对该数据的查询就会命中缓存，直接返回空，避免了请求轰炸数据库。
2. **缓存击穿**：指一个热点Key在某个时刻突然失效，导致大量并发请求瞬间都打到数据库上。我的解决方案是使用**互斥锁**。当缓存未命中时，只有第一个请求能获取到锁，然后去查询数据库并写回缓存，其他请求则在等待。这样就避免了大量请求同时冲击数据库。
3. **缓存雪崩**：指在某一时刻，大量的缓存Key同时过期，导致所有请求都涌向数据库，可能造成数据库宕机。我的解决方案是**设置随机过期时间**。在给缓存Key设置过期时间时，我在基础时间上增加一个随机值（比如1-5分钟），这样可以错开Key的过期时间，避免集中失效。

### 3. JVM与并发

**面试官**：简单聊一下JVM吧。在你的代码沙箱中，当用户代码执行时，你如何确保它不会因为创建过多对象或死循环而耗尽系统资源？

**求职者**：这主要通过两层限制来保证：
1. **Docker层面的资源限制**：我们在启动每个代码沙箱的Docker容器时，通过参数`--memory`限制了容器能使用的最大内存，通过`--cpu-quota`限制了CPU的使用率。这样从根本上杜绝了单个用户代码影响整个宿主机的可能性。
2. **应用层面的超时控制**：我们有一个**守护线程**来监控每个判题任务的执行时间。如果在规定时间内（比如2秒）没有执行完毕，守护线程会强制中断该任务所在的线程，并销毁Docker容器，从而释放资源。

通过这种**外部监控**和**底层隔离**的方式，我们有效地防止了用户代码对系统的潜在破坏。
